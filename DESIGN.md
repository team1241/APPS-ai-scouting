# Scouting administration

## Visual direction

Bumper numbers. FRC robots carry their team number in big white numerals on blue or red bumper fabric, and that is how mentors and scouts recognise a team across the pits. The app takes that one move. The shell (header, navigation rows, page band and footer) is a saturated bumper-blue field, and team numbers lead in heavy, wide white numerals. Work happens below the field on a cool light ground with white rounded surfaces. It should feel like a friendly product, not a corporate console: pill controls, soft depth, generous type, plain language.

Adult team leads use laptops in brightly lit event venues and phones between tasks, so the interface stays light, with strong contrast and 44px targets. The colours do not assert any FRC team's branding; the sky highlight comes from the Theory6 Apps badge.

## Foundation

Next.js App Router, Tailwind CSS v4 and HeroUI v3 (`@heroui/react`, `@heroui/styles`, built on React Aria). HeroUI needs no provider; `globals.css` imports `tailwindcss` then `@heroui/styles` and overrides HeroUI's tokens on `:root`. The html element carries `light` and `data-theme="light"`. Prefer HeroUI components (Button, Card, Chip, TextField, Select, Checkbox, RadioGroup, Tabs, Modal, AlertDialog, Alert, Skeleton, EmptyState) over hand-built controls, and style them through their props and Tailwind classes. Next.js links that look like buttons use `LinkButton` (`components/link-button.tsx`, `buttonVariants` on `next/link`).

Type: Mona Sans (variable, with its width axis) for all UI text, loaded through `next/font/google` as `--font-mona`; Martian Mono (`--font-mona` sibling `--font-martian`, the Tailwind `font-mono`) only for values people copy or compare: API keys, question codes, versions in meta lines. Two display utilities live in `globals.css`: `font-bumper` (weight 900, width 125, tabular figures) for team numbers, versions and the entrance headings, and `font-display` (weight 800, width 112.5) for page titles, wordmarks and section headings. Body copy is regular, controls semibold.

Colour tokens (OKLCH, `globals.css`): `--bumper` (the field and the accent), `--bumper-deep` (footer, pressed states, text on white buttons on the field), `--bumper-raised`, `--bumper-ink` (secondary text on the field) and `--sky` (highlight on the field). HeroUI's semantic tokens are tuned to match: `--accent` is the bumper blue, `--background` is a cool off-white, `--surface` white, `--muted` a blue-grey that keeps 4.5:1 on white, and success, warning and danger each have readable `-soft-foreground` values. Use the HeroUI utilities (`bg-surface`, `text-muted`, `bg-accent-soft`, `text-danger`, `shadow-surface`, `divide-separator`). Text selection, the caret and focus rings use the palette.

## Components and layout

Surfaces are white, 16px radius (`rounded-2xl`), with HeroUI's soft surface shadow and no border; declare elevation once. Lists are one surface with `divide-separator` rows. Buttons and chips are pills. Buttons keep a 44px minimum height except the `sm` size. The accent marks actions, selection and the field; state colours appear only where they carry meaning.

Every page has the same frame: the sticky blue header, an optional blue navigation row (team or operator), then `PageHeading` (`components/page-heading.tsx`), a blue band holding the page title in `font-display` (30px, 36px from `sm`), an optional description in `--bumper-ink`, optional actions on the right and an optional back link above. A team workspace title leads with the team number in bumper numerals (56–96px) above the team name. Content follows in `PageBody`, the same `max-w-6xl` column as the header and band, so left and right edges line up. Long-form text (privacy notice) keeps a reading measure inside it.

Error, denied-access, loading and empty states use plain actionable language. Loading states (`components/loading-skeletons.tsx`) repeat the frame: a blue band with translucent title bars, then surface skeletons shaped like the loaded cards and lists (`LoadingPage`, `CardSkeleton`, `ListSkeleton`, `Bar`). Each keeps a screen-reader-only status message; the skeleton pulse stops under reduced motion.

Short forms open in `FormDialog` (`components/form-dialog.tsx`, HeroUI Modal): an optional icon tile, title, one line of description, the form, and `DialogActions` stacked on phones with the primary action on top. It stays open while pending, shows errors inside and closes on success. Destructive confirmations use `ConfirmDialog` (HeroUI AlertDialog with a danger icon): a quiet danger ghost trigger, a focused "Keep …" action and a danger action. Confirmations for destructive actions use this dialog by default, not inline buttons.

The public access application uses TanStack Form with Zod validation and HeroUI TextField, Select and Checkbox. The page heading leads directly into the form without introductory paragraphs. Controls have visible labels and focus, with full-width fields and a full-width primary action on phones. Validation uses inline FieldError messages and focuses the first invalid control; server failures add an actionable error summary; service failure preserves entered values. Pending submission disables the controls and names the operation. A successful submission replaces the form, inside the same card, with a receipt that distinguishes pending review from granted access.

## Accessibility

Visible keyboard focus, a skip link, semantic headings, labeled actions, reduced-motion-aware loading and text status alongside any visual state. The circuit traces' one-time draw-in on the public band is the only decorative motion, and it is off under reduced motion. HeroUI's press feedback and overlay transitions follow its reduced-motion handling. Do not add other unnecessary motion, profile displays, analytics or session replay.

## Administration navigation

The header is the bumper field: the Theory6 Apps logo (`apps/web/src/assets/apps-logo.png`) clipped to its circle at 40px with a white ring, a "Theory6" wordmark in `font-display` and a sky "Administration" label on wider screens. Together they are the home link, with an accessible name and visible focus. It returns signed-in users to team selection and signed-out users to the public entrance. The header sticks to the top of the viewport. From tablet width (`sm`) up, a workspace's team navigation row sticks directly below it; on phones it scrolls away with the page to save height. Both publish their rendered heights (`--site-header-height`, `--sub-header-height`, 0 while the row is not sticky), so the row and the page's scroll padding follow wrapping.

The header navigation is pills: Home, and Teams when signed in; the current section is a lighter pill. On phones the header stays one row (about 60px): signed-in users do not see Home there, because the logo already leads to Teams, and the wordmark is hidden. Signed-out users see a quiet Request access link (hidden on phones and on the request page) and a white Sign in pill. While account state loads, show a short loading status. The footer is `--bumper-deep` with the Theory6 Apps wordmark and the Privacy link. Signed-in users have the Clerk profile button in the header; account settings and sign-out live in its menu.

Inside a workspace, the team navigation row (on the field, below a faint divider) shows the backend-authorized team as a white bumper plate (`TeamPlate`) and name, then Workspace and Scouting specifications as tabs with a white underline on the current page, and Change team in sky only when the current backend response contains more than one authorized team. It uses the page's existing access result, never a Clerk organization claim or URL-derived label. Loading and denied/unavailable pages do not assert a selected team. Long names wrap and controls keep 44px hit areas without a hamburger menu.

Team selection ("Choose your team") is a stack of surface rows: a blue bumper tile with the team number in white bumper numerals, then the name and role, then a chevron. Rows lift slightly on hover.

## Admin headings and status

`TeamNumber` sets a team number in bumper numerals in the accent colour with a screen-reader "Team" prefix, for lists. `TeamPlate` is the white plate used on the field.

States use `StatusBadge` (`components/status-badge.tsx`), a HeroUI soft Chip pill with a dot and a text label. Tones are success (Connected, Signed in), waiting (accent; pending work), warning (status unavailable), danger (failed or expired) and neutral (not started). The text carries the state; colour only reinforces it.

## Telegram connection

The workspace's Telegram card is compact. The title and its status badge share the first line, followed by one line on what the connection does. Connected: the line starts with the connection date, and a quiet Disconnect sits on the right (below the text on phones) and opens the confirmation dialog. Unavailable: a warning badge and a "Check again" action in the same place. Not connected: below a divider, two numbered steps, "Create a one-time link" and "Open it in Telegram and tap Start". The first step shows a check once a link exists. The second shows an "Open Telegram" button (new tab), a countdown to the link's expiry and a note that the page updates on confirmation. While the link is valid and the tab is visible, the page polls the connection state every 3 seconds and refreshes when it connects. An expired link shows a danger message and keeps "Create a new link" available.

## API keys

The team workspace has an "API keys" card below Administrators, in the same card style: a title and one line on read-only scope and shared admin access. Each active key is a row with its name, created date and rate limit, then the key in a monospace field. The key is masked after its first 10 characters until the admin selects Show; a key the admin just created starts shown. Copy writes the full key to the clipboard and changes to "Copied" for 2 seconds; if the clipboard fails, the key is shown with a short error. Revoke is a quiet destructive button that opens `ConfirmDialog` ("Keep key" / "Revoke key"). With no keys, the card shows HeroUI `EmptyState` below a divider: a key icon in a soft accent tile, "No API keys yet", one line on what keys are for, and the "Create key" button. Once keys exist, that button moves to the top right of the card. It opens a dialog (same panel as `ConfirmDialog`) with a "Key name" field, one line on replacing a key (create, update the integration, revoke the old one), and Cancel / Create key actions. The dialog stays open while creating, shows errors inside it, and closes on success. Unavailable keys show a "Check again" action and no create button. On phones the key field takes the full width and the buttons wrap below it.

## Administrators

The team workspace has an "Administrators" card between Telegram and API keys, in the same card style: a title, one line on what admins manage, and an "Invite administrator" button at the top right. Each admin is a row with name and approval date, a neutral "You" badge for the viewer and a neutral "Not signed in yet" badge for an approval that is not linked. Pending invitations follow under an "Invited" subheading, each with name, email, expiry and inviter, and a status badge: "Email sent" or "Waiting to accept" (waiting tone), or "Email not sent" (danger tone). Email invitations have an outline Resend; every invitation has a quiet destructive "Cancel invitation" that opens `ConfirmDialog` ("Keep invitation" / "Cancel invitation"). The invite dialog uses the API key dialog panel: one line on how invitations reach the person, Name and Email fields, the adult and authorization attestation checkbox, errors inside the dialog, and Cancel / Send invitation. It closes on success and the card shows a success status line. Unavailable data shows a "Check again" action and no invite button.

On team selection, invitations for the signed-in account appear above the team list under "Invitations": a surface row with the team number column, team name, inviter and expiry, and a primary "Accept and open team" action that goes straight to the team. With an invitation, an account with no teams sees no "No approved teams" card and is not sent to `/operator`.

## Operator review

`/operator` is an admin surface in the light register. Platform operators reach it from an "Operator" item in the main header navigation, after Teams, shown only when the backend confirms operator access. It carries a sky count of applications waiting for review. An operator with no team who opens `/admin` goes straight to `/operator`. The page has two surface lists: "Waiting for review" (oldest first) and "Recently reviewed". Each row leads with the team number in a fixed 96px column (`TeamNumber`), then the applicant name, and role and email in muted text. An empty list is one muted line, not a card.

A pending row adds the submitted date and a "Check team on The Blue Alliance" link (new tab), then, indented under the applicant on wider screens, a team name field prefilled with "Team <number>" and a primary "Approve and invite" action on the same line. Reject is a quiet destructive text button that opens a confirmation dialog (`ConfirmDialog`, HeroUI AlertDialog): a white 20px-radius panel over a blue-tinted scrim, a danger icon, a question title, one line on the consequence, a focused "Keep reviewing" action and a danger "Reject application" action. Buttons stack on phones with the destructive action first. The dialog stays open while the action runs, shows any error inside it, and closes on success. A successful approve or reject redirects to `/operator?approved=<id>` or `?rejected=<id>`; the page reads the outcome back from the reviewed list and shows a dismissible notice above the lists (success tint, or destructive tint when the invitation was not sent) and highlights that row. Reviewed rows show a `StatusBadge` and its date: Signed in, Invited, Rejected, or "Invitation not sent" in the danger tone. Approved rows that are not signed in keep "Resend invitation". Controls keep 44px hit areas and stack to full width on phones.

Operator pages share a navigation row on the bumper field: a deep-blue "Platform operator" scope chip with a sky shield icon, then Applications, with a sky count of waiting applications, All teams and Operators, as tabs with a white underline on the current page. On phones the row is a full-width segmented control instead: three equal 44px tabs on a deep-blue track, the current one a white pill, the waiting count as a small sky badge on the Applications tab; the chip is screen-reader only there, since the header's Operator pill and the page description carry the scope; All teams stays underlined on a team's detail page. It lives in the operator layout, so it stays in place while the page below loads. The Operators page lists operators with who added them, marks the viewer with a neutral "You" badge and no Remove action, and has an "Add operator" button beside the "Current operators" heading. It opens a dialog (the same panel as the API key dialog) with one line on what happens for people with and without an account, Name and Email fields, errors inside the dialog, and Cancel / "Add or invite" actions. It closes on success and a success status line appears under the heading. Remove opens the same confirmation dialog ("Keep operator" / "Remove operator"). Confirmations for destructive actions use this dialog by default, not inline buttons. Open invitations appear below the operator list under "Invited", with an Invited, Expired or Not sent badge, the email, expiry and inviter, an outline Resend action and a quiet destructive Cancel invitation that opens the same confirmation dialog ("Keep invitation" / "Cancel invitation"). The dialog's submit button reads "Add or invite".

## Scouting specifications

The team navigation row carries two links after the team name, Workspace and Scouting specifications, as tabs on the field (white underline on the current page; drafts and publications keep the specifications link current). The workspace has a "Scouting specifications" summary card that is one link with draft and publication counts.

The list page groups by season (a `font-display` heading, "2027 season") and then by kind, each kind a surface card with a muted header row. Draft rows have a waiting "Draft" badge, the edit time, "Continue editing" and a quiet destructive "Delete draft". Publication rows are one link: a `vN` version in accent bumper numerals in a 48px column (other version names appear as code in the meta line), the name, publication date and event names, a success "Used at N events" badge (under the text on phones) and a chevron. The empty state uses HeroUI `EmptyState` with a clipboard icon. "New specification" opens the dialog panel with Season and Name fields and radio cards for Kind and Start from.

The draft editor is one column, 60rem wide. It reads like the conversation scouts have: each question is a surface row whose first line is the follow-up question in the foreground at 18px, then label, code (monospace), answer summary and requirement in muted text, then each rule as an accent sentence. A 24px gutter between the number and the text holds a dot per question and draws each rule dependency as a sky line from the question it reads to the question it changes; lines that touch the selected question are accent and thicker. On phones the number moves inside a 24px dot and the separate number column goes, so question text starts about 56px from the card edge; the lines are drawn from each dot's measured position and run in the card's left padding. The text always carries the same facts. The selected row has a 2px accent ring and opens in place, below a divider: Move up, Move down, Duplicate and Remove, then the fields in two columns on wider screens. Identity rows have a deep-blue "Identity" pill with a sky lock, and an expanded identity row starts with a deep-blue note. Rules sit on an accent panel with their sentence at the top and dropdowns for effect, question, comparison and value. Every builder dropdown, including the New specification dialog and the preview and test tabs, uses `ChoiceSelect` (`components/specifications/choice-select.tsx`): the HeroUI Select with a 44px white trigger, a popover list below it and a check on the chosen item. An empty value such as "Not stated" is a real choice. A stored value that no longer exists (a deleted option or question) is listed in destructive text so the admin can see and replace it.

From 64rem up, the Edit tab is two panes. The outline sits on the left (24rem) with tighter rows and a right chevron, and the selected question opens in a sticky inspector on the right instead of in place (`question-inspector.tsx`). The inspector header shows "Question N of M", the label, and icon actions (move up, move down, duplicate, remove, close); a required identity question shows why it cannot be removed instead of a remove action. Below it, "In Telegram" (`telegram-view.tsx`) shows how the question reaches scouts. The bot never asks questions one at a time: it replies once with every missing answer, identity questions first and on their own, so "This question" shows that single reply built by the shared `followUpQuestion`, with this question's sentence marked and chips for when it is asked; an optional question says the bot never asks for it. "Full example" replays a sample exchange through `finalizeWithEvaluation`, ending with the bot's "Saved! Thanks for scouting.", and needs a draft without problems. Then Question, Answer and Rules tabs (HeroUI Tabs) hold the same fields as the single-column layout, each tab with a danger count of its problems. A problem link opens the tab that holds the field, scrolls it into view and focuses it. Escape or close returns focus to the question's row. With nothing selected the right pane is a dashed placeholder. Below 64rem the outline opens questions in place as before.

A fixed bar at the bottom holds the save status (`StatusBadge`: Saved in success, Unsaved in neutral, Saving in waiting, Not saved in danger, edited elsewhere in warning), a danger problems count that opens the summary, Add question (wider screens) and "Review and publish". On phones it is two rows with a full-width publish button. Problems also appear under each field and in a destructive-tint summary above the questions. A conflict replaces nothing: a warning panel offers "Keep my version" and "Load their version". The publish dialog shows Season, Kind and Version as three cells in bumper numerals.

Below the draft heading, a tab row (Edit with its question count, Preview answers, Test extraction) uses an underline tab row: muted text, a 2px accent underline on the current tab, arrow-key movement. Each tab keeps its inputs. The bottom bar stays on every tab; Add question shows only on Edit. When the draft has problems, Preview and Test show one destructive-tint panel with the count and "Show problems", which returns to Edit with the summary open. A summary of three problems or fewer shows its list straight away. Inside an open question, Escape closes it and returns focus to its row. A required identity row says it cannot be removed instead of showing a disabled Remove.

Preview answers is one surface list in the outline's order: number, the follow-up in the foreground, label, answer summary and the current requirement, a `StatusBadge` on the right (Answered success, Missing and Cannot use answer danger, Waiting on another answer waiting, Not asked and Not answered neutral), then a control for the sample answer (text, number, a Not stated / Yes / No dropdown, an option dropdown, or checkboxes with "Set to none of these" and Clear). Under the control: the reason in one plain sentence, each rule as a small pill (Applies in accent, Does not apply in muted, Not known yet in warning) with its rule sentence, and a muted note when an answer is kept as history. An Outcome card above the list shows Complete (success) or Needs follow-up (warning), the answered count and the follow-up as an accent message bubble. Test extraction has a Sample messages card (note, replies with the follow-up they answer, character counts, Add reply, a privacy line, Run test) and a Result card: the same outcome row and bubble, each message with its stated values as accent chips, and a table of answers after every message. Errors appear in a destructive-tint line inside the card and never clear the sample. An out-of-date result has a warning-tint line.

The publication page leads with the version in bumper numerals and the name, a neutral "Published, read-only" badge with a lock and "Create editable draft". After publishing, a success notice says no event uses the version yet. The Events card lists the season's events with what new sessions use; "Use for new sessions" and "Stop using" open the dialog panel that says open sessions keep their version. The questions follow in the editor's outline, read-only, with details in a definition list.

## Public entrance

The signed-out home page, `/sign-in`, `/sign-up` and `/request-access` share the bumper-blue entrance band (`PublicBand`, `components/public-band.tsx`) with `CircuitTraces`, authored SVG linework from the Theory6 Apps badge, in sky at low opacity. It draws in once on load and is static under reduced motion. On phones a mask keeps the traces away from text and actions.

- Headings use `font-bumper`, with the second word in sky. No gradient text.
- The badge is clipped to its own circle with a white ring. The home page has no badge in the band; the sign-in, sign-up and request pages show a small badge on wider screens only.
- On the band, the primary action is a white pill with deep-blue text; the secondary action is a white outline pill. Focus rings are sky.

Home: the band fills the space between header and footer. "Team administration" and "Sign in to choose your team.", then Sign in and Request access, in one left-aligned column. A strip along the bottom of the band holds the approved-adult line and the native Access requirements disclosure. Do not add scouting-process copy or promotional claims.

Sign in and Accept invitation: the band holds the heading and one line. The Clerk card overlaps the band edge (`overlapCard`: white, 16px radius, soft blue shadow, no border), themed through `authCardAppearance` (hex copies of the bumper blue and foreground, Mona Sans, a pill primary button, 44px controls). Clerk's own header is hidden.

Request access: the band holds only the heading. The form sits in the same overlapping card. The receipt replaces the form inside the same card; do not nest a second card.

## Operator team directory

`/operator/teams` ("All teams") uses the operator page layout. The description says the list covers every team and that opening a team does not make the operator an admin. A labelled "Team number or name" search field sits above the list with an outline Search button (full width on phones), as a plain GET form. The list heading names the scope ("Registered teams" or "Teams matching “…”") with the count, and a "Clear search" link when searching. Each row is one link: the team number in the `TeamNumber` column (96px, 64px on phones), the name, the registration date, then admin, signed-in and active key counts. A warning badge marks "No signed-in admin"; a waiting badge counts invitations. A chevron ends the row. Pages of 25 end with a "1–25 of N" line and outline Previous and Next buttons. Empty, no-match and past-the-end states are one muted line.

A team's detail page starts with an "All teams" back link, then the workspace-style heading (number, name) and one line saying the operator sees the team as an operator, not an admin, and can remove its administrators and revoke its keys. Two cards follow, as in the team workspace. Administrators: rows with name, approval or admin date, a badge, "Signed in" (success), "Not signed in yet" (neutral) or "No web access" (warning), and a quiet destructive Remove that opens `ConfirmDialog` ("Keep administrator" / "Remove administrator"). The dialog names the person and team, says they stay as a scout and their invitations are cancelled, and warns when they are the last admin. Then "Invited" rows with expiry, inviter and the team list's invitation badges, without emails or actions. API keys: rows with name, an Active (success) or Revoked (neutral) badge, created date and rate limit. Active keys use the workspace key field, masked after the stored start, with Show/Hide and Copy; the value loads only on Show or Copy and is dropped on Hide. The buttons name the pending action ("Showing…", "Copying…") and errors appear under the field. Active keys also have a quiet destructive Revoke that opens `ConfirmDialog` ("Keep key" / "Revoke key"), naming the key and team. Revoked keys show their start and say the value was erased. There is no create action.
