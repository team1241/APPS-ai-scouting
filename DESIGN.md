# Scouting administration

## Visual direction

Adult team leads use laptops in brightly lit event venues and phones between tasks. Two registers share one system. A navy frame (header, footer and the public entrance band) carries the character of the Theory6 Apps badge: navy, sky blue and circuit linework. Admin content inside the frame stays light and restrained, with clear grouping and a blue action accent. The colours come from the badge; they do not assert any FRC team's branding.

## Foundation

Next.js App Router with Tailwind CSS and locally owned shadcn/ui New York components. Archivo is the shared sans-serif for headings, body text, controls and Clerk components. Load the Latin variable font, with its width (`wdth`) axis, through `next/font/google` with swap display and metric-adjusted fallback; Next.js serves the font from the app rather than making browser requests to Google. Use regular weight for body copy and medium/semibold for controls. Display headings and wordmarks use extra-bold at width 125 (`font-stretch-125%`), shared through `displayHeading`. Semantic HTML and a compact typography scale remain the foundation. Colors use OKLCH CSS variables in `apps/web/src/app/globals.css`, including `--navy`, `--navy-raised`, `--sky` and `--sky-soft` for the frame. Text selection uses the sky tint.

## Components and layout

Buttons and cards live in `apps/web/src/components/ui`. Keep corners at 8–12px and reserve the accent for actions and selection. Field outlines use `--color-input` (light grey, slightly stronger than card borders); checkboxes use a stronger muted outline so the small box stays visible. Admin surfaces use borders, not decorative shadows. The one exception is a public card that overlaps the navy band (request form, Clerk sign-in): it uses a soft navy shadow and no border. Desktop content is centered; organization rows remain readable and clickable on phones. Error, denied-access, loading and empty states use plain actionable language. Loading states are skeletons that match the loaded page: heading and description bars, then the same bordered lists, fields and buttons, in the `--color-skeleton` tint. Each keeps a screen-reader-only status message, and the pulse runs only when reduced motion is off.

The public access application uses TanStack Form with Zod validation and shadcn Field, Input, Select and Checkbox components. The page heading leads directly into the form without introductory paragraphs. Controls have visible labels and focus, with full-width fields and a full-width primary action on phones. Validation uses inline FieldError messages and focuses the first invalid control; server failures add an actionable error summary; service failure preserves entered values. Pending submission disables the controls and names the operation. A successful submission replaces the form, inside the same card, with a receipt that distinguishes pending review from granted access.

## Accessibility

Visible keyboard focus, a skip link, semantic headings, labeled actions, reduced-motion-aware loading and text status alongside any visual state. The circuit traces' one-time draw-in is the only decorative motion, and it is off under reduced motion. Do not add other unnecessary motion, profile displays, analytics or session replay.

## Administration navigation

The header and footer are navy on every page and frame the light admin content. The header sticks to the top of the viewport while the page scrolls, and a workspace's team navigation row sticks directly below it. Both publish their rendered heights (`--site-header-height`, `--sub-header-height`), so the row and the page's scroll padding follow wrapping on narrow screens and in-page link targets land below the bars. The header shows the supplied Theory6 Apps logo (`apps/web/src/assets/apps-logo.png`), clipped to its circle at 44px, with a "Theory6" wordmark (Archivo width 125) and a sky "Administration" label on wider screens. Together they are the home link, with an accessible name and visible focus. It returns signed-in users to team selection and signed-out users to the public entrance.

The header exposes labeled navigation: Home, and Teams when signed in. The current location has white text and a sky underline. Signed-out users see a quiet Request access link (hidden on phones and on the request page) and a sky Sign in button. While account state loads, show a short loading status. The footer shows the Theory6 Apps wordmark and the Privacy link. Do not leave the logo as the only usable header element. Omit scouting-process explanations and Telegram reminders from the ordinary administration interface.

Signed-in users have the Clerk profile button in the same header position across screens; account settings and sign-out live in its menu. This is the requested account control, not an additional profile display. Privacy remains available in the footer.

Inside a workspace, a secondary navigation row displays the current backend-authorized team number and name with an explicit Change team action only when the current backend response contains more than one authorized team. It uses the page's existing access result, never a Clerk organization claim or URL-derived label. Loading and denied/unavailable pages do not assert a selected team. Long names wrap, controls retain at least 44px hit areas, and narrow layouts can wrap the team action onto another line without a hamburger menu.

Team-selection lists clip hover backgrounds to their rounded container. Row focus outlines sit inside the row so keyboard focus remains visible within that clipping.

## Admin headings and status

Admin page titles use `PageHeading` (`apps/web/src/components/page-heading.tsx`): the entrance's Archivo extra-bold at width 125, in navy, 30px on phones and 36px from `sm`. Team numbers lead in the same face through `TeamNumber`, in the primary blue with tabular figures and a screen-reader "Team" prefix. The team workspace title is the number followed by the team name. Team selection ("Choose your team") rows start with the number in a fixed 80px column, then the name and role, and end with a lucide chevron.

States use `StatusBadge` (`apps/web/src/components/status-badge.tsx`): a pill with a dot and a text label. Tones are success (Connected, Signed in), waiting (pending work), warning (status unavailable), danger (failed or expired) and neutral (not started). The text carries the state; colour only reinforces it. The tones come from `--color-success`, `--color-warning` and their `-soft` backgrounds in `globals.css`.

## Telegram connection

The workspace's Telegram card has a title, one line on what the connection does and a status badge at the top right. Connected: a footer row with the connection date and a quiet Disconnect that opens the confirmation dialog. Not connected: two numbered steps, "Create a one-time link" and "Open it in Telegram and tap Start". The first step shows a check once a link exists. The second shows an "Open Telegram" button (new tab), a countdown to the link's expiry and a note that the page updates on confirmation. While the link is valid and the tab is visible, the page polls the connection state every 3 seconds and refreshes when it connects. An expired link shows a destructive message and keeps "Create a new link" available. Unavailable status shows a warning badge and a "Check again" action.

## API keys

The team workspace has an "API keys" card below Administrators, in the same bordered style: a title and one line on read-only scope and shared admin access. Each active key is a row with its name, created date and rate limit, then the key in a monospace field. The key is masked after its first 10 characters until the admin selects Show; a key the admin just created starts shown. Copy writes the full key to the clipboard and changes to "Copied" for 2 seconds; if the clipboard fails, the key is shown with a short error. Revoke is a quiet destructive button that opens `ConfirmDialog` ("Keep key" / "Revoke key"). With no keys, the card shows the shadcn `Empty` state below a solid divider: a key icon in an accent tile, "No API keys yet", one line on what keys are for, and the "Create key" button. Once keys exist, that button moves to the top right of the card. It opens a dialog (same panel as `ConfirmDialog`) with a "Key name" field, one line on replacing a key (create, update the integration, revoke the old one), and Cancel / Create key actions. The dialog stays open while creating, shows errors inside it, and closes on success. Unavailable keys show a "Check again" action and no create button. On phones the key field takes the full width and the buttons wrap below it.

## Administrators

The team workspace has an "Administrators" card between Telegram and API keys, in the same bordered style: a title, one line on what admins manage, and an "Invite administrator" button at the top right. Each admin is a row with name and approval date, a neutral "You" badge for the viewer and a neutral "Not signed in yet" badge for an approval that is not linked. Pending invitations follow under an "Invited" subheading, each with name, email, expiry and inviter, and a status badge: "Email sent" or "Waiting to accept" (waiting tone), or "Email not sent" (danger tone). Email invitations have an outline Resend; every invitation has a quiet destructive "Cancel invitation" that opens `ConfirmDialog` ("Keep invitation" / "Cancel invitation"). The invite dialog uses the API key dialog panel: one line on how invitations reach the person, Name and Email fields, the adult and authorization attestation checkbox, errors inside the dialog, and Cancel / Send invitation. It closes on success and the card shows a success status line. Unavailable data shows a "Check again" action and no invite button.

On team selection, invitations for the signed-in account appear above the team list under "Invitations": a bordered row with the team number column, team name, inviter and expiry, and a primary "Accept and open team" action that goes straight to the team. With an invitation, an account with no teams sees no "No approved teams" card and is not sent to `/operator`.

## Operator review

`/operator` is an admin surface in the light register. Platform operators reach it from an "Operator" item in the main header navigation, after Teams, shown only when the backend confirms operator access. It carries a sky count of applications waiting for review. An operator with no team who opens `/admin` goes straight to `/operator`. The page has two bordered lists: "Waiting for review" (oldest first) and "Recently reviewed". Each row leads with the team number in a fixed 96px column (`TeamNumber`), then the applicant name, and role and email in muted text. An empty list is one muted line, not a card.

A pending row adds the submitted date and a "Check team on The Blue Alliance" link (new tab), then, indented under the applicant on wider screens, a team name field prefilled with "Team <number>" and a primary "Approve and invite" action on the same line. Reject is a quiet destructive text button that opens a confirmation dialog (`ConfirmDialog`, built on the Radix alert dialog): a white 12px-radius panel over a navy scrim, a question title, one line on the consequence, a focused outline "Keep reviewing" action and a destructive "Reject application" action. Buttons stack on phones with the destructive action first. The dialog stays open while the action runs, shows any error inside it, and closes on success. A successful approve or reject redirects to `/operator?approved=<id>` or `?rejected=<id>`; the page reads the outcome back from the reviewed list and shows a dismissible notice above the lists (success tint, or destructive tint when the invitation was not sent) and highlights that row. Reviewed rows show a `StatusBadge` and its date: Signed in, Invited, Rejected, or "Invitation not sent" in the danger tone. Approved rows that are not signed in keep "Resend invitation". Controls keep 44px hit areas and stack to full width on phones. The destructive button variant uses `--color-destructive-foreground` for its label.

Operator pages share a white secondary navigation row: a navy "Platform operator" scope chip with a shield icon (icon only on phones), then Applications, with a primary count of waiting applications, All teams and Operators. The current page is underlined in the primary colour; All teams stays underlined on a team's detail page. It lives in the operator layout, so it stays in place while the page below loads. The Operators page lists operators with who added them, marks the viewer with a neutral "You" badge and no Remove action, and has an "Add operator" button beside the "Current operators" heading. It opens a dialog (the same panel as the API key dialog) with one line on what happens for people with and without an account, Name and Email fields, errors inside the dialog, and Cancel / "Add or invite" actions. It closes on success and a success status line appears under the heading. Remove opens the same confirmation dialog ("Keep operator" / "Remove operator"). Confirmations for destructive actions use this dialog by default, not inline buttons. Open invitations appear below the operator list under "Invited", with an Invited, Expired or Not sent badge, the email, expiry and inviter, an outline Resend action and a quiet destructive Cancel invitation that opens the same confirmation dialog ("Keep invitation" / "Cancel invitation"). The dialog's submit button reads "Add or invite".

## Public entrance

The signed-out home page, `/sign-in` and `/request-access` share a navy entrance band (`PublicBand`, `apps/web/src/components/public-band.tsx`). Its character comes from the Theory6 Apps badge: navy (`--navy`), sky blue (`--sky`, `--sky-soft`), circuit-trace linework and the mascot badge. The admin pages keep the light interface.

- Headings use Archivo at width 125 and extra-bold weight, with the second word in sky blue. No gradient text.
- `CircuitTraces` is authored SVG geometry at low opacity. It draws in once on load and is static under reduced motion. On phones a mask keeps the traces away from text and actions.
- The badge is clipped to its own circle. The home page has no badge in the band; the header logo is enough. The sign-in and request pages show a small badge on wider screens only. The supplied logo has no transparency, so the circle clip trims the edge of the “6”; a transparent export would fix this.
- On the band, the primary action is sky blue with navy text; the secondary action is outlined in sky. Focus rings are sky blue with a navy offset.

Home: the band fills the space between header and footer. “Team administration” and “Sign in to choose your team.”, then Sign in and Request access, in one left-aligned column. A strip along the bottom of the band holds the approved-adult line and the native Access requirements disclosure. Sign in always shows, so every environment, including local worktrees, needs the Clerk keys in `apps/web/.env.local`. Do not add scouting-process copy or promotional claims.

Sign in: the band holds “Welcome back” and the one-line approval note. The Clerk SignIn card overlaps the band edge like the request form, themed through `appearance` (hex copies of navy and foreground, Archivo, navy flat primary button, 44px controls). Clerk's own header is hidden because the band carries the heading. The site header omits its Sign in button on this page.

Accept invitation (`/sign-up`): the same layout as sign-in, with "Accept your invitation" (with "invitation" in sky blue) and one line asking for the invited email. The Clerk SignUp card shares the sign-in theme (`authCardAppearance`).

Request access: the band holds only the heading. The form sits in a white card (12px radius, soft navy shadow, no border) that overlaps the band edge. The submit action is navy. The receipt replaces the form inside the same card with a sky check mark; do not nest a second card.

## Operator team directory

`/operator/teams` ("All teams") uses the operator page layout. The description says the list covers every team and that opening a team does not make the operator an admin. A labelled "Team number or name" search field sits above the list with an outline Search button (full width on phones), as a plain GET form. The list heading names the scope ("Registered teams" or "Teams matching “…”") with the count, and a "Clear search" link when searching. Each row is one link: the team number in the `TeamNumber` column (96px, 64px on phones), the name, the registration date, then admin, signed-in and active key counts. A warning badge marks "No signed-in admin"; a waiting badge counts invitations. A chevron ends the row. Pages of 25 end with a "1–25 of N" line and outline Previous and Next buttons. Empty, no-match and past-the-end states are one muted line.

A team's detail page starts with an "All teams" back link, then the workspace-style heading (number, name) and one line saying the operator sees the team as an operator, not an admin, and can remove its administrators and revoke its keys. Two bordered cards follow, as in the team workspace. Administrators: rows with name, approval or admin date, a badge, "Signed in" (success), "Not signed in yet" (neutral) or "No web access" (warning), and a quiet destructive Remove that opens `ConfirmDialog` ("Keep administrator" / "Remove administrator"). The dialog names the person and team, says they stay as a scout and their invitations are cancelled, and warns when they are the last admin. Then "Invited" rows with expiry, inviter and the team list's invitation badges, without emails or actions. API keys: rows with name, an Active (success) or Revoked (neutral) badge, created date and rate limit. Active keys use the workspace key field, masked after the stored start, with Show/Hide and Copy; the value loads only on Show or Copy and is dropped on Hide. The buttons name the pending action ("Showing…", "Copying…") and errors appear under the field. Active keys also have a quiet destructive Revoke that opens `ConfirmDialog` ("Keep key" / "Revoke key"), naming the key and team. Revoked keys show their start and say the value was erased. There is no create action.
